# ============================= trace.json 字段说明 =============================
# 该 json 文件用于记录“预处理阶段的抽样轨迹（trace）”，目的是在生成 h5 之后，
# 仍然能够追踪每一个 split、每一个工况、每一个类别到底是如何从原始 txt 文件中
# 抽取样本的。该文件不参与模型训练，而是用于：
# 1) 检查当前预处理是否满足设定的不平衡小样本抽样要求；
# 2) 检查某个类别-某个工况下的数据是否只来自其对应的两个原始文件；
# 3) 检查当常规滑窗不够时，是否启用了“错位重叠采样”；
# 4) 检查最终抽到的样本起点位置，以及每个样本来自哪个文件；
# 5) 方便复现实验、论文撰写和后续排查数据问题。
#
# ----------------------------- 顶层字段说明 -----------------------------------
# split_name
#   表示当前 trace 文件对应哪个数据划分。
#   常见取值包括：
#   - "train"：训练集对应的抽样轨迹
#   - "val"  ：验证集对应的抽样轨迹
#   - "test" ：测试集对应的抽样轨迹
#   例如：
#   PHM_spur8_T1_train_trace.json 中的 split_name 一般为 "train"。
#
# entries
#   为一个列表（list）。
#   列表中的每一个元素表示一个“类别-工况”的完整抽样记录。
#   更准确地说：
#   一条 entry = 当前 split 下，某一个 condition（工况）中，某一个 class（类别）
#   的全部抽样信息。
#   例如：
#   - train 中 30hz_High 工况下 spur 3 类别的抽样记录
#   - train 中 35hz_High 工况下 spur 7 类别的抽样记录
#   - test  中 45hz_High 工况下 spur 1 类别的抽样记录
#   都会分别对应 entries 中的不同元素。
#
# --------------------------- entries 中每条记录说明 ----------------------------
# split_name
#   表示该条 entry 所属的数据划分。
#   它与顶层的 split_name 通常一致，这里重复保留是为了让单条 entry 脱离上下文后
#   也能独立判断它属于 train / val / test 中的哪一个。
#
# condition
#   表示当前这条记录对应的工况名称。
#   工况通常由“转速 + 负载”共同组成，例如：
#   - "30hz_High"
#   - "35hz_High"
#   - "40hz_High"
#   - "45hz_High"
#   它表示当前抽样统计是在这个工况域下进行的。
#
# domain_id
#   表示当前工况在本次任务中的整数域标签编号。
#   这个编号与最终 h5 文件中的 domain 数组是一致的。
#   例如：
#   如果当前任务的 domain_map 为：
#     {
#       "30hz_High": 0,
#       "35hz_High": 1,
#       "40hz_High": 2,
#       "45hz_High": 3
#     }
#   那么当 condition = "30hz_High" 时，domain_id 就会是 0。
#
# class_name
#   表示当前这条记录对应的类别名称，即原始数据集中对应的类别文件夹名。
#   例如：
#   - "spur 1"
#   - "spur 2"
#   - ...
#   - "spur 8"
#   它表明当前正在统计哪个类别在当前工况下的抽样情况。
#
# class_label
#   表示该类别在最终 h5 文件中的整数标签值，即 y 数组中的类别编号。
#   该值由配置文件中的 class_folders 顺序决定。
#   例如：
#     class_folders = ["spur 1", "spur 2", ..., "spur 8"]
#   则通常会对应：
#     "spur 1" -> 0
#     "spur 2" -> 1
#     ...
#     "spur 8" -> 7
#
# is_normal
#   表示当前类别是否被视为“正常类”。
#   取值为布尔类型：
#   - true  ：当前类别是正常类
#   - false ：当前类别是故障类
#   该字段非常重要，因为你的不平衡抽样策略中，正常类与故障类的抽样数是不同的。
#   例如在 200:1 设定下：
#   - 正常类每个源域抽 200 个样本
#   - 每个故障类每个源域抽 1 个样本
#   所以 is_normal 用于说明当前 entry 应该套用哪套抽样数。
#
# requested_sample_count
#   表示“该类别在该工况下，本来计划抽取多少个样本”。
#   这是目标抽样数，不代表一定已经成功抽满。
#   例如：
#   - 对 train split 中的正常类，可能 requested_sample_count = 200
#   - 对 train split 中的故障类，可能 requested_sample_count = 1
#   - 对 test split 中的故障类，可能 requested_sample_count = 20
#
# files
#   这是一个列表，表示当前“类别-工况”组合下，具体使用了哪些原始 txt 文件。
#   正常情况下，对于 PHM spur8 数据，一个类别在一个工况下通常会有两个原始文件，
#   因此 files 列表通常会包含两个元素。
#   files 中的每一个元素，表示“某一个原始 txt 文件”的抽样详细信息。
#
# actual_sample_count
#   表示当前“类别-工况”组合最终实际抽到了多少个样本。
#   正常情况下它应该等于 requested_sample_count。
#   如果二者不相等，说明当前两个文件在“常规滑窗 + 错位重叠采样”之后仍然不足，
#   或者代码执行中发生了异常。
#   因此该字段是检查当前数据是否真的抽满的重要指标。
#
# --------------------------- files 列表中每个元素说明 --------------------------
# file_path
#   表示当前参与抽样的原始 txt 文件路径。
#   例如：
#   "D:/.../spur 3/spur 3_30hz_High_1.txt"
#   通过这个字段可以精确定位当前样本来自哪个类别目录下的哪个原始采样文件。
#
# signal_length
#   表示该 txt 文件中读取出的原始一维振动信号长度。
#   这里的信号是你要求的“第二列：输出侧振动”。
#   signal_length 越大，理论上可切出的滑窗数量越多。
#
# base_candidate_count
#   表示该文件在“常规滑窗采样”下能够生成的候选窗口数量。
#   这里的常规滑窗通常是：
#   - 窗长 = win_len
#   - 步长 = stride
#   从起点 0 开始依次切分
#   例如：
#   起点可能为 [0, 1024, 2048, ...]
#   则 base_candidate_count 就是这类常规不偏移窗口的总个数。
#
# overlap_candidate_count
#   表示当常规滑窗不足时，在该文件内部额外构造出的“错位重叠采样”候选窗口数量。
#   这些窗口依然来自当前文件本身，不会借用其他工况、其他类别或其他域的数据。
#   与 base 不同之处在于：
#   它们使用了额外的 offset（偏移量），例如：
#   - stride/2
#   - stride/4
#   - 3*stride/4
#   形成新的窗口起点，如：
#   [512, 1536, 2560, ...]
#   这些起点与 base 的起点不同，因此不会与常规滑窗完全重合。
#
# total_candidate_count
#   表示当前文件中可用于抽样的总候选窗口数。
#   其定义为：
#     total_candidate_count = base_candidate_count + overlap_candidate_count
#   它代表在该文件内部，按照“常规滑窗 + 错位重叠采样”后，理论上最多能提供多少个不同窗口。
#
# selected_count
#   表示最终从当前这个文件中实际抽到了多少个样本。
#   注意，这是“最终被选中的窗口数量”，而不是候选窗口总数。
#   例如：
#   如果某个类别某个工况需要抽 5 个样本，而它有两个文件，
#   则 selected_count 可能表现为：
#   - 文件1抽到 3 个
#   - 文件2抽到 2 个
#
# selected_base_count
#   表示最终选中的样本中，有多少个来自“常规滑窗候选池（base）”。
#   也就是说，这部分样本是通过普通滑窗直接得到的，不需要额外错位补样。
#
# selected_overlap_count
#   表示最终选中的样本中，有多少个来自“错位重叠采样候选池（overlap）”。
#   这说明当前文件中常规滑窗不够时，额外使用了带偏移量的新窗口。
#   若该值大于 0，说明当前文件确实触发了“错位重叠补样”机制。
#
# selected_starts
#   表示最终从该文件中抽到的所有窗口起点位置，是一个整数列表。
#   每个数字表示一个样本窗口在原始一维信号中的起始索引。
#   例如：
#   selected_starts = [0, 1024, 1536]
#   说明：
#   - 有一个样本从 0 开始切
#   - 有一个样本从 1024 开始切
#   - 有一个样本从 1536 开始切
#   结合 win_len，你就可以精确还原每个窗对应的原始时域片段。
#
# selected_modes
#   与 selected_starts 一一对应，表示每个被抽中的窗口是通过哪种方式产生的。
#   它通常是一个字符串列表，长度与 selected_starts 完全相同。
#   常见取值包括：
#   - "base"    ：表示该窗口来自常规滑窗
#   - "overlap" ：表示该窗口来自错位重叠采样
#   例如：
#   selected_starts = [0, 1024, 1536]
#   selected_modes  = ["base", "base", "overlap"]
#   则表示：
#   - 起点 0 的窗口来自普通滑窗
#   - 起点 1024 的窗口来自普通滑窗
#   - 起点 1536 的窗口来自错位重叠采样
#
# ----------------------------- 字段之间的关系说明 ------------------------------
# requested_sample_count 与 actual_sample_count 的关系
#   requested_sample_count 表示“计划抽多少”
#   actual_sample_count    表示“最终实际抽到了多少”
#   正常情况下二者应相等。
#   若不相等，说明当前 class-condition 组合在严格限制“只能使用当前两个文件”的前提下，
#   即便加上错位重叠采样，也无法满足设定的抽样数。
#
# selected_count 与 selected_base_count / selected_overlap_count 的关系
#   对于 files 列表中的每个文件，都有：
#     selected_count = selected_base_count + selected_overlap_count
#   它表示从当前文件中抽到的总样本数，等于“普通滑窗样本数 + 重叠补样样本数”。
#
# total_candidate_count 与 base_candidate_count / overlap_candidate_count 的关系
#   对于 files 列表中的每个文件，都有：
#     total_candidate_count = base_candidate_count + overlap_candidate_count
#   它表示当前文件理论上能提供的全部候选窗口数量。
#
# selected_starts 与 selected_modes 的关系
#   两者是一一对应的。
#   也就是说，第 i 个 selected_starts 对应的采样方式，就是第 i 个 selected_modes。
#   因此你可以通过它们精确知道：
#   某个具体样本来自哪里、从哪里开始切、是普通滑窗还是错位重叠补出来的。
#
# ----------------------------- 这个 json 怎么读 --------------------------------
# 当你想看“某个类别在某个工况下的数据到底来自哪里”时，
# 你应该先在 entries 中定位到对应的：
#   condition + class_name
# 然后查看该 entry 下的 files 字段。
#
# 如果你想看“这个类别一共抽了多少样本”，看：
#   requested_sample_count
#   actual_sample_count
#
# 如果你想看“这些样本分别来自哪两个文件”，看：
#   files -> file_path
#
# 如果你想看“某个文件本来能切多少常规窗口”，看：
#   files -> base_candidate_count
#
# 如果你想看“某个文件后来额外生成了多少错位重叠窗口”，看：
#   files -> overlap_candidate_count
#
# 如果你想看“当前文件最终到底用了哪些窗口”，看：
#   files -> selected_starts
#
# 如果你想判断“这些窗口是普通滑窗还是重叠补样”，看：
#   files -> selected_modes
#
# ----------------------------- 这个 json 的实际用途 -----------------------------
# 1. 用于验证不平衡抽样是否正确
#    例如 train 中正常类是否真的是 200，故障类是否真的是 1/5/10。
#
# 2. 用于验证某个类别-工况的数据是否只来自该工况对应的两个文件
#    因为 files 中明确记录了 file_path，所以可以直接核对来源。
#
# 3. 用于验证是否触发了错位重叠采样
#    只要 selected_overlap_count > 0，或者 selected_modes 中出现 "overlap"，
#    就说明当前文件在常规滑窗不够时，已经启用了你要求的“错开一部分”的补样方式。
#
# 4. 用于后续论文或实验记录
#    当你需要说明“每个类每个工况的样本来自哪两个原始采样文件、是否均衡、是否触发补样”
#    时，这个 trace.json 就是直接证据。
#
# 5. 用于排查异常
#    如果某个类在某个工况下抽不到足够样本，你可以通过：
#    - base_candidate_count
#    - overlap_candidate_count
#    - selected_count
#    快速定位究竟是原始信号过短、窗口设置过大，还是抽样数设得太高。
#
# ------------------------------ 一句话总结 ------------------------------------
# 这个 trace.json 本质上就是“预处理抽样审计日志”。
# 它完整记录了每个 split 中，每个工况、每个类别、每个原始文件的候选窗口数量、
# 最终选中样本数量、选中窗口起点以及采样方式，从而保证你的不平衡小样本域泛化
# 数据预处理过程是可检查、可追踪、可复现的。
